# 开发与扩展流程

## 接手开发：产品决策与工作顺序

本节整理 2026-11-01 与项目发起人逐步确认的开发要求，供接手者理解取舍和推进顺序。
它约束 local-ai 的产品开发，不把仓库开发规则变成助手执行日常任务的限制。
需求或设计调整时，同次更新本节、实现和使用文档。

### 产品定位与边界

local-ai 是日常工作助手，可排障、写脚本、处理数据、配置服务，并准备、提交和跟踪
Slurm/Kubernetes 作业。列举的任务、工具和硬件不是白名单。
查询真实系统应使用工具采集证据，不编造结果或只让用户代执行。
仓库开发、纯计划测试和 GPU 部署资源检查，不能扩大为禁止普通硬件查询或用户要求的计算作业。
编写脚本、提交作业和任务完成是不同结果，应分别说明。

GPU 服务端负责推理；BCM 客户端用当前用户权限执行文件、Shell、Git、SSH 等工具。
访问模型 API 与通过 SSH 操作其他机器是两条不同路径。

### 已确认的设计取舍

| 用户反馈形成的问题 | 后续开发应保持的行为 |
|---|---|
| 安装失败只显示“找不到镜像” | 区分正常 inspect 缺失与真正 pull 失败，显示实际错误和完整日志位置；metadata.db 缺失查 Docker/containerd 存储，不能归因于模型或源码目录 |
| 希望共享镜像和模型材料 | 区分可共享权重/镜像导出包与运行时数据库；--data-dir 不移动 Docker/containerd 存储，多节点不能共享其活动数据库；新方案单独验证 |
| BCM 本来就能访问 GPU 节点 | 模型使用可达 API endpoint；内置 SSH 隧道及相应 client doctor 已移除，转发交给外部 frp/nginx 等工具；日常 SSH 运维仍可使用 |
| 希望用宿主机 IP 连接 | 显式配置 --host；0.0.0.0 是监听地址，endpoint 填实际主机名/IP；不悄悄改变已有监听或网络设置 |
| 容器运行却看不出进展 | 启动提示日志路径和查看方法，区分启动、加载、就绪、失败；READY 依据健康检查，不由 docker ps、端口开放或空白 curl 输出推断 |
| 日志分散、返回值难懂 | 安装到 install.log，实例运行到 instances/NAME/server.log；终端清楚提示，JSON 留在 stdout，进度/诊断在 stderr，退出码与状态一致 |
| 退出聊天后无法照原生提示恢复 | opencode -s ID 找回原 endpoint、项目与私有状态；用公开接口查询，兼容空列表与项目范围，不依赖内部数据库表 |
| OpenCode 接管复制但复制失败 | 默认终端选取与复制粘贴，关闭客户端鼠标捕获和剪贴板快捷键；说明点击/滚轮停用的取舍，验证终端模式 |
| 固定客户端版本妨碍升级或离线使用 | 参考版本是验收记录，不是运行白名单；复用安装、识别导入版本、允许选版/离线包，按实际接口验证候选版本 |
| 模型会更新，也可能换模型 | 仓库/revision、目录、服务名、引擎参数和客户端能力按配方配置；独立模型锁；新配方不继承实机验收，不套用 DeepSeek 专用参数 |
| 目录式安装与迁移 | 解压目录即安装根，普通 src/ 保存源码；install 就地准备角色资源，export 默认生成 dist/ 完整离线包；排除 dist/、实例状态、个人历史和凭据；换目录后重新安装并配置本机资源 |
| 一个 BCM 连接多个模型服务 | 初始默认 endpoint 可选；后续用 config 或编辑文件修改配置，不用重新安装；chat --endpoint/--model 本次覆盖不改写默认值；各 endpoint 历史与缓存隔离，恢复时找回原连接，不静默回退到默认节点 |
| 源码脚本如何发布 | 当前按 main 与具体提交交付；测试通过不自动触发打 tag，正式版本须经用户明确要求和质量评估 |
| 单用户速度与首次编译尖峰 | 保留原配方，显式选择 DSpark 与有限推理预热；API READY 不等于 WARMUP COMPLETE，编译缓存按配方持久化，重启使完成记录失效；记录实际覆盖范围与并发取舍 |
| 约 400 ms TTFT 是否过高 | 记录方法、输入规模、缓存/负载及端到端/首 token 耗时再判断；不混淆启动编译、生成前延迟与思考内容，不凭单个数值给结论 |

上表记录设计理由，具体操作以[命令手册](commands.md)和[部署指南](deployment.zh-CN.md)为准。

### 每次需求的推进顺序

1. **理解结果与执行位置。** 读本节、AGENTS、README、相关命令/模块和验证记录；
   分清修改 local-ai 与用助手处理外部任务，不混用两种工作流程。
2. **复现并采集证据。** 使用本次任务已授权的连接与账户，确认执行主机。
   能直接获取日志就不要求用户反复转贴。读完整相关输出，记录失败步骤、退出码和实际错误；
   摘要、省略输出、终端快照不能冒充完整证据。
3. **定位层次再改动。** 分开检查宿主机/容器运行时、存储/网络、推理引擎、客户端和外层终端。
   不把 containerd 错误当成 image 不存在，也不凭其他窗口能复制就断言所有剪贴板路径正常。
4. **实现可配置、可检查的结果。** 固定身份用于复现选定材料，不是版本或模型白名单。
   保留业务服务与用户状态；新模型、平台和候选客户端在独立目录验收。
   同时考虑提示、日志、退出码与恢复，不仅让底层命令执行成功。
5. **做匹配的验证。** 运行本页 unittest、Ruff、diff 检查；客户端适配跑原生验收，
   新模型验证流式/推理/工具往返；硬件与作业集成按实际授权和资源另测。
   覆盖拒绝、旧状态和退出清理，不削弱既有用例来通过测试。
   不能从服务端测试推断外层终端真实复制成功；未测平台、模型或集群写清边界。
6. **从用户入口同步文档。** 更新逐级帮助、README、中英文手册/部署说明和验证记录；
   走查首次安装路径，让用户知道在哪执行、看哪份日志、何时算成功、失败后如何处理。
7. **提交并交付。** 审查暂存文件，排除模型、二进制、缓存、凭据和真实基础设施原始日志。
   本项目协作中“提交代码”包含 commit 与 push；完成已授权推送后核对远端提交并查看 CI。
   清理自己创建的临时进程/资源，不影响现有业务。
   说明改动、原因、验证、限制和生效方法；CI 未完成或仅 CPU 验证时如实报告。


## 开发规则的适用范围

本页约定用于修改 local-ai 仓库；普通系统与硬件运维任务不需要先走开发流程。
项目指令在根目录 [AGENTS.md](../AGENTS.md)。只有 `server plan --inventory FILE`
这一纯计划功能不得额外探测硬件、启动子进程或写文件；不限制用户要求的本机或 SSH 硬件查询。
客户端的通用运维指引由 [operations.py](../src/local_ai/operations.py) 提供，
每次 `chat` 启动时写入私有会话目录并通过客户端配置加载。

## 项目配置文件

`pyproject.toml` 是 Python 项目的构建和开发配置，日常运行源码中的 `./local-ai` 无需修改它。

| 配置节 | 本项目的用途 |
|---|---|
| `build-system` | 使用 setuptools>=68 构建安装包 |
| `project` | 包名 cluster-local-ai、版本 1.1.0、Python>=3.10；运行时第三方依赖为空 |
| `project.scripts` | 安装后的 local-ai 命令调用 local_ai.cli:main |
| `tool.setuptools` | 从 src 查找模块，并将 profiles.json 包含到安装包 |
| `project.optional-dependencies` | dev 组包含 Ruff 0.14.2，仅开发时安装 |
| `tool.ruff` | Python 3.10 兼容目标、100 字符行宽和静态检查规则 |

仓库根目录的 Bash 脚本 `local-ai` 将 src 加入 PYTHONPATH 后运行同一入口。
模型、GPU 及 vLLM 参数由 profiles.json/profiles.py 管理；使用者查[命令手册](commands.md)。

## 文档交付要求（每次修改必做）

文档正确性属于交付条件。任何实现、默认值或说明修改后，必须仔细检查 README、命令手册、部署、离线、架构、开发、优化探索及验证文档的中英文版本；即使某份无需修改，也要确认它与改动不冲突。不得只搜索替换出错的那一行就结束。

1. **README 是入口。** 按首次使用者的顺序走查：前提、获取源码、安装、配置、启动、就绪、日志、客户端使用及迁移入口。关键步骤不能缺失，不能要求读者自行猜测其他文档中的前提。
2. **核对实际行为。** 参数、默认值、保存配置、执行位置、输出和退出码须与 --help、实现及验证记录一致；区分安装程序、运行数据和用户私有状态。
3. **示例完整且一致。** 全项目主流程使用 GPU001、bcm-headnode、/raid/local-ai、实例 a 和端口 18000。第二实例 b/18001 只在双实例章节引入，并同时给出服务端与客户端命令。目录、用户、模型和地址改变时先说明原因。
4. **逐步可执行。** 写明在哪台机器、以哪个用户、从哪个目录执行；参数来源、生成文件、日志路径和成功标志清楚。安装已保存的 endpoint 不再写成 chat 必填；临时覆盖与持久设置分别说明。每条示例检查引号、命令顺序和前置文件。
5. **简洁且职责清楚。** README 保留一条完整主流程；部署指南展开特殊配置和故障；命令手册集中参数；完整导出、转移、导入步骤只在离线指南维护，保留两条可独立执行的路线；README 说明源/目标角色并链接过去。跨文档引用具体章节，避免整段复制、重复命令和尾部追加同义章节。
6. **中英文同步。** 两种语言采用相同主机、路径、端口、默认值、步骤和验收边界。历史验证必须标明时间与旧行为，不能冒充当前安装说明。
7. **检查全部引用。** 验证相对链接、章节锚点、源码下载地址和版本状态；删除 tag 或调整标题时同步修复所有入口。没有成熟稳定版本时明确开发状态，不把源码版本号当作稳定承诺。
8. **完成检查后交付。** 运行现有文档契约检查（Bash 语法、CLI 示例、链接及参数覆盖），并人工通读主流程与中英文差异。自动检查不能替代语义检查。在提交说明中列出检查范围、修正的不一致及尚未验证事项；发现冲突先修订，再提交。

## 准备环境与执行检查

运行时代码仅使用 Python 标准库。可选开发工具安装在项目虚拟环境，不写入系统 Python：

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -e '.[dev]'
.venv/bin/python -m unittest discover -s tests -v
.venv/bin/ruff check src tests scripts
.venv/bin/ruff format --check src tests scripts
git diff --check
```

`pip install -e '.[dev]'` 以可编辑方式安装当前项目及 dev 工具；代码改动无需重复安装。
`unittest -s tests` 从 tests 目录发现测试，`-v` 显示测试名；`ruff check` 检查规则，
`ruff format --check` 只检查格式不改文件；`git diff --check` 检查补丁空白错误。

CPU CI 检查策略与失败边界，无法证明 CUDA 内核兼容性、硬件最低内存、互联拓扑或吞吐。

## 接手开发与提交约定

1. 先读 README 的拓扑和使用手册，再读架构及验证记录；真实环境信息和原始日志保留在忽略目录，不能带进提交。
2. 命令入口集中在 cli.py；新增命令须提供逐级 --help、参数含义、默认值、执行位置，并同步中英文手册。
3. GPU/CPU/镜像平台与客户端架构独立；新增型号优先添加 profiles.json 配置和测试清单，不写真实主机名或 GPU UUID 到逻辑中。
4. 引擎参数只从 profiles.py 生成；固定模型 revision、镜像清单与平台摘要，不能用可变标签代替版本身份。
5. plan 在使用给定硬件清单时不得运行子进程或写文件；启动前再检查真实占用、CDI 和平台。
6. 安装诊断经 installlog.py 集中记录，JSON 标准输出与进度标准错误分离；不能把预期的缺失探测误标为安装失败。
7. 本地复用必须验证完整性并区分版本已核实/未核实；不得伪造版本锁。离线导入同时保留归档校验和内容身份检查。
8. 修改后运行本页的 unittest、Ruff 和 diff 检查；测试失败先修复，不能通过删改既有验收用例来“通过”。
9. 新平台和 GPU 测试写明来源、分配设备、版本、方法、结果、限制；CPU 测试不能提高硬件验证等级。
10. 发布前审查暂存文件，记录提交、依赖版本和验收结果；确认临时容器、客户端进程和资源已清理，再推送并查看 CI。

新增 GPU 的标准流程见本页“新增硬件配置”一节。B200 或后续型号拿到硬件后再新增并验收，不能修改已验证配置来冒充新型号支持。

## 新增硬件配置

1. 核对上游模型配方，以及目标 OS 实际可见的 GPU 数、显存、CPU 架构、互联和主存。
2. 确认镜像清单提供目标平台，记录固定的清单摘要及平台子摘要。
3. 在 `src/local_ai/profiles.json` 添加架构、平台、本地 TP 数、Engram 位置、
   GPU 类型、保守显存保护值和验证级别。
4. 引擎参数统一在 `profiles.py` 生成；不在 BCM 客户端加入 GPU 分支，也不从服务端推断客户端架构。
5. 测试有效与无效选择、编号/UUID 重复、缺失设备、CPU/镜像不匹配和内存不足。
6. 使用 `server plan --inventory FIXTURE.json` 检查计划。
   只有 plan 接受测试清单，start 必须发现真实硬件。
7. 在已分配硬件上准备固定镜像和权重，启动后等待 API，测试流式输出和原生工具往返，
   再从 BCM 执行真实的编辑、测试和 hostname 任务；检查内存及日志，最后停止实例。
8. 将版本、方法、结果及限制写入 [验证记录](validation.md)。
   不能仅凭单元测试把配置标记为实机验证通过。

同一 OS 只有两张 GPU 的 GB300 需要 TP2 配置和足够主存。
跨 OS 的张量并行属于新的编排能力，不能只修改配置 JSON 来实现。

## 新增或升级模型

同时修改固定仓库/revision、分词器/解析器、模型目录和客户端能力声明。
验证流式结束、思考内容传输、工具调用/结果往返，以及真实文件编辑和测试。
不能把已有服务模型名静默指向另一个 revision。
思考预算或量化变更要与运行时优化分别记录。

## 客户端与离线资源

原生程序按 BCM 的架构选择，与服务端平台独立。
在线安装固定 NPM 版本，并在提取、执行允许的二进制前校验 SHA256/SHA512。
导入程序需检查 ELF 架构、可选 SHA256 和请求的版本。
CPU 架构一致不等于完整 ABI 兼容，还需检查发行版、共享库和 CPU 指令支持。

资源包只包含程序、允许的公共缓存和清单，不包含历史、认证文件或 SSH 密钥。
模型权重与 CPU 架构无关；镜像、原生程序及缓存中的可执行文件与架构有关，
不能混用 AMD64 与 ARM64 缓存。

优化理由、实际引擎参数、失败尝试和下一步问题保存在[探索记录](performance.md)；实测数字集中在 validation.md，操作命令集中在部署指南。实验改变取舍时一并更新。即便当前只管理 vLLM，也保留 SGLang 的测试结果与边界，避免接手者重复摸索。

## 推理预热功能变更

模型专属投机解码及图捕获尺寸留在配方，不改全局默认参数。warmup.py 仅由显式 server warmup 或 start --warmup 触发；导入模块、plan、status、install 均不得生成合成推理请求。status 读取 warmup.json，核对配置摘要与容器 StartedAt。

变更须覆盖部分失败、期限与取消、重复预热拒绝、错误部署元数据、API 精确 token 数及重启后记录失效。在已分配 GPU 上用独立进程、独立缓存比较有无显式预热，流式请求载荷保持一致，同时测量首次与后续请求。保留现有业务，区分磁盘缓存复用与进程内 CUDA Graph，不能把有限覆盖写成消除全部 JIT。证据见[验证记录](validation.md)。

## 测试与评审原则

- 使用给定清单的计划生成应确定、无子进程和文件写入。
- 测试拒绝状态及退出清理，不只检查正常命令。
- 导入镜像后核对配置/层身份，不能只核对 tag。
- 验证两个会话的历史稳定、端点连接配置独立。
- 用 hostname 验证工具在 BCM 执行，不能只看模型回复成功。
- 原始日志及实际基础设施标识保存在被忽略的运行目录，只提交脱敏汇总。
- CI 不得启动 GPU 工作或修改集群状态、固件、网络。
- 重构与发布时保留现有生产服务状态。

推送前检查暂存文件，排除权重、二进制、缓存、凭据和私有路径，并执行全部检查。
源码、测试、文档与 CI 一并提交；新增平台尽量保持变更集中，
具备验收证据后才提高其验证级别。


## 模型与客户端兼容性

默认 DeepSeek 配方不是模型白名单。profiles.json 的 models 保存仓库、revision、
model_directory、served_name、镜像、engine_options、environment 和 client 能力；
default_model 选择默认客户端模型，硬件 profile 的 model 字段选择服务端配方。
profile 的 engine_options 覆盖模型的同名选项；对象/数组编码为 JSON，true 发出独立开关，
false/null 省略。监听、端口、模型路径和 TP 参数仍由管理命令控制。
DeepSeek 解析器、Engram 和推理格式只属于其配方，不自动用于其他模型。

复制内置 profiles.json 到自己的文件，添加模型与 profile，再设置：

```bash
export LOCAL_AI_CATALOG=/home/alice/local-ai-profiles.json
./local-ai profiles
```

每个新模型/revision 使用独立 model_directory。锁位于该目录内的 model.lock.json；
旧版根级锁仅在仓库与目录匹配时复用。客户端可用 chat --model 选择其他
OpenAI-compatible 模型，在 client 中声明 reasoning、tool_call、interleaved 和 limit。
未登记模型不自动套用 DeepSeek 的上下文或推理格式。新增配方不继承原配方的实机验证等级。

当前下载器面向 Hugging Face snapshot，权重校验面向带索引的分片 safetensors，
服务端使用 vLLM；其他权重格式或引擎须增加适配。配置可生成不等于模型工具调用或硬件已验收。

客户端不设运行时版本白名单。省略 client install --version 时复用已安装版本，
导入本地程序时识别其版本，仅首次在线下载使用参考版本；也可显式指定版本。
在线源失效时使用现有安装、本地程序或离线包。升级候选放在独立 --client-dir，运行：

```bash
PYTHONPATH=src .venv/bin/python scripts/check-client.py --client-dir /home/alice/client-candidate
```

脚本用临时状态、原生会话 HTTP API 和伪终端检查恢复、公开 JSON 元数据、
鼠标关闭和终端粘贴模式，不调用 GPU 或模型生成。CI 自动检查参考版本；
手动工作流的 client_version 可测试候选版本。外层终端真实复制、模型工具往返和
历史迁移仍需验证。切换前退出客户端并备份历史；跨数据库迁移回退时恢复原备份。

## 交付与版本标记

当前按 main 分支和具体提交交付开发源码，现有 v1.0.0、v1.1.0 标签已撤下，源码版本号不代表稳定性。完成测试与 CI 是基本条件，不自动代表达到正式版本质量。未经用户明确要求，不创建 tag 或 GitHub Release。

日常交付：检查实现与全部文档，完成适当验证，提交并推送，核对远端提交和 CI。后续用户明确要求正式版本时，再评估完整安装路径、文档一致性、兼容性及已知问题；确认质量后同步版本号、验收记录，并在确切通过 CI 的提交上创建标签。保留具体提交可用于复现与回退。

## 目录式安装实现

paths.py 根据启动脚本位置决定根目录，不取终端 cwd，也不写死 /raid/local-ai；显式 --data-dir 和 LOCAL_AI_DATA_DIR 保留兼容。deployment.py 就地准备资源并记录相对的安装设置；bundle.py 流式导出程序、模型、镜像归档和客户端，生成整包及逐文件 SHA256。config/catalog.json 随包携带配方。程序为普通目录，不使用隐藏版本目录或源码链接。导出排除自身 dist/ 和个人状态。安装不启动 GPU；新主机用本机 GPU、端口和 endpoint 创建实例。
